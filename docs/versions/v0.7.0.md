# v0.7.0 卡组构筑与第二挑战

## 1. 版本信息

- 日期：2026-11-08
- 状态：执行中
- 主题：让抽卡与升级真正改变出战构筑，并提供序列 8 后的第二挑战
- 用户价值：收藏、抽卡和升级从资源积累转为可感知的牌组决策

## 2. 版本目标

完成以下可保存、可重复的路径：

```text
启动 / 继续
  -> 选择白昼身份
  -> 编辑或选择一套 8 张卡的合法牌组
  -> 首次路线或已解锁挑战
  -> 战后奖励 / 祈愿 / 升级
  -> 将新卡和升级结果加入下一次牌组
  -> 完成第一挑战后解锁第二挑战
  -> 使用数据驱动修饰与路线变体完成挑战
  -> 保存牌组、挑战解锁和结算结果
```

本版本验证构筑深度与重复游玩，不扩展第二条途径、多城市或开放世界。

## 3. 必须交付

### 3.1 卡池与牌组构筑

- 将占卜家正式卡池从 8 张扩展到至少 16 张。
- 新增卡只能复用已注册 effect 闭集，或按变更流程登记新 effect；不得在 UI 写卡牌特例。
- 初始拥有至少 8 张卡，保证玩家第一次进入构筑页面即可形成合法牌组。
- 首版牌组固定选择 **8 张唯一卡牌**，只能使用已拥有卡牌。
- 支持查看收藏、筛选、加入/移除、清空、恢复初始牌组、合法性提示和三套本地预设。
- 牌组选择必须在首次路线和挑战战斗前生效；战斗中不修改牌组。

### 3.2 第二挑战

- 第一挑战完成后解锁第二挑战，并保存稳定完成记录。
- 第二挑战至少使用一个数据驱动遭遇变体或节点覆盖，不得复制 RouteEngine。
- 至少增加 2 个新挑战修饰，和既有 3 个修饰形成不同构筑压力。
- 第二挑战开始前展示解锁条件、已选修饰、路线差异、预期奖励和失败保留规则。
- 挑战奖励继续通过 `ProgressionEngine.apply_reward_bundle()` 入账，同一完成检查点不重复发奖。

### 3.3 玩法设计

- 维护 `src/core/**`、`src/gameplay/**`、`tests/gameplay/**`、`data/cards/**`、`data/enemies/**`、`data/encounters/**`、`data/routes/**`、`data/rituals/**`、`data/challenges/**`、`data/decks/**`。
- 定义卡组合法性、预设、出战选择、第二挑战解锁和路线覆盖语义。
- 复用现有路线/战斗/成长/挑战引擎，不另建第二套流程。
- 提供只读 DeckSnapshot、DeckCommand/Result、ChallengeSnapshot 扩展和稳定原因码。
- 覆盖未拥有卡、重复卡、空牌组、未完成预设、非法路线覆盖和重复领奖。

### 3.4 数值设计

- 校准新增 8 张卡的费用与升级曲线，确保至少存在防御、灵性/抽牌、标记爆发三条可理解构筑方向。
- 对至少三套 8 卡牌组、两个身份和两个挑战进行固定种子真实引擎采样。
- 记录胜率、完成率、平均回合、休息选择、关键卡使用率、升级收益和资源产出。
- 不以单一最优牌组为设计目标；若某套牌组无可行胜利路径，前向调整卡牌或内容，不堆全局血量。
- 只编辑 `data/balance/**`、`tools/simulation/**`、`tests/simulation/**` 和本角色报告。

### 3.5 本地数据层开发

- 为卡池、卡组、预设、当前牌组和第二挑战完成记录建立 schema。
- 存档升级到 v5，保留 v1/v2/v3/v4 迁移、备份和损坏保护。
- 提供 DeckContentPort、应用用例和只读摘要；不计算牌组合法性或挑战解锁。
- 继续游戏恢复到最近已确认节点，同时保留当前牌组和预设。

### 3.6 UI 设计

- 新增卡组编辑/收藏页面、牌组选择入口和第二挑战入口。
- 展示已拥有/未拥有、升级等级、费用、目标、当前牌组数量和合法/非法原因。
- 只读取 DeckSnapshot；命令包括选择预设、加入/移除、保存预设、确认出战、开始挑战。
- 第二挑战复用挑战选择/路线/结算页面，但必须显示路线变体和修饰。
- 对 v0.7 美术候选在实际界面审稿并记录通过、退回或仅 UI 适配。

### 3.7 美术

- 为新增卡牌制作无文字 512×400 卡面候选。
- 制作卡组编辑/收藏背景、第二挑战徽记与至少两个新修饰图标。
- 正式候选先进入 `art/**`，由主协调者迁移到 `assets/game/v0.7.0/**`。
- UI 与美术保持独立，美术不得自行验收。

### 3.8 产品经理与主协调者

- 在实现前冻结 DeckCommand、DeckSnapshot、卡组 schema、v5 存档和第二挑战解锁。
- 检查新增卡是否复用事实源，阻止 UI/数值复制卡牌逻辑。
- 完成短循环、首次路线、第一挑战、第二挑战和牌组恢复的全链路回归。
- 重新导出 Windows 独立构建，在项目目录外验证牌组、挑战和继续游戏。

## 4. 卡组规则

- 首版牌组大小：8 张唯一卡牌。
- 玩家必须拥有每张所选卡。
- 新增卡加入收藏后立即可进入牌组。
- 卡牌升级等级随卡牌实例进入后续战斗。
- 默认初始牌组固定且合法，不依赖抽卡。
- 每套预设保存卡牌稳定 ID 列表，不保存显示名或资源路径。
- 预设不存在或含未拥有卡时，UI 显示原因并允许恢复初始牌组；不得静默替换已选卡。

## 5. 第二挑战建议基线

- 稳定 ID：`challenge.v070.broken_procession`
- 解锁：序列 8 且完成 `challenge.v060.mirror_echoes`
- 路线：复用首次路线骨架，通过数据覆盖改变至少一个遭遇组成或节点效果。
- 新修饰候选：
  - 仪式干扰：仪式错误额外增加污染，但成功奖励提高。
  - 双影追击：精英节点加入第二个敌人，完成奖励提高。
- 最终 ID、数值和机制由玩法/数值/数据层在 v0.7 接口冻结阶段确认。

## 6. 依赖顺序

```text
卡牌池与 Deck 领域契约
  -> Deck/Challenge schema 与 v5 存档
  -> UI 卡组编辑与第二挑战页面
  -> 美术候选和 UI 实机审稿
  -> app 路由与真实战斗/挑战接线
  -> 三构筑数值采样
  -> 全量回归与 Windows 独立构建
```

并行边界：

- 玩法先冻结卡牌、牌组和第二挑战语义。
- 数值不得在玩法定义之前创建第二套卡牌数据。
- UI/美术可在契约下并行制作，但 UI 必须实机审稿。
- 共享 `src/core/**` 仍由玩法独占，`data/schema/**` 由数据层独占。

## 7. 验收标准

- 正式占卜家卡池至少 16 张，所有卡牌 ID 唯一、效果可注册、升级定义完整。
- 新游戏初始拥有至少 8 张卡，可以立即保存一套合法 8 卡牌组。
- 牌组编辑拒绝未拥有、重复、无效和数量错误，并给出稳定原因码。
- 当前牌组和三套预设保存后重启可恢复，首次路线和挑战都实际使用所选牌组。
- 抽到的新卡可进入牌组；升级后的卡牌在下一战实际生效。
- 未完成第一挑战时第二挑战保持锁定，完成后可解锁且不能伪造完成。
- 第二挑战至少包含一个非血量路线差异和两个新修饰，固定种子可复现。
- 挑战奖励只入账一次，失败不清空局外收藏、等级、预设或已确认奖励。
- UI 不计算牌组合法性、解锁、挑战效果、奖励或卡牌金额。
- v0.7 UI 完成实际美术审稿。
- 全部玩法、数据层、UI、集成、数值、主场景与独立构建检查退出码 0。
- 无绝对运行时路径、循环依赖、重复事实源或测试资源进入正式构建。

## 8. 明确非目标

- 第二条途径、更高序列或 22 途径系统。
- 多城市、开放世界、自由行走或多人联机。
- 完整 20 卡以上收藏与商业美术替换。
- 付费抽卡、广告、账号、云存档和运营系统。
- 途中换牌、战斗内编辑牌组或通用 mod 框架。

## 9. 风险与质量门

| 风险 | 预防 | 处理 |
|---|---|---|
| 新增卡牌造成第二事实源 | 全部效果与金额只在 data/cards | 前向合并回单一数据源，UI/数值不复制 |
| 牌组预设保存显示名或资源路径 | schema 只保存稳定 ID | 迁移旧字段并增加校验 |
| 唯一最优牌组 | 三套牌组真实采样、不同挑战验证 | 调整机制/费用，不做全局血量堆叠 |
| 第二挑战复制路线规则 | 复用 RouteEngine，只覆盖数据 | 退回重复规则实现，改端口/覆盖 |
| UI 重算牌组合法性 | DeckSnapshot 提供原因码 | UI 只显示与提交命令，适配层前向修复 |
| v5 迁移损坏旧档 | 逐版本迁移、备份、原件保护 | 失败明确报错，不覆盖原档 |
| 新内容拖慢首个可玩版本 | 先完成 8 卡牌组闭环，再增加卡面 | 保障核心闭环，扩展内容分批提交 |

## 10. 下一版本入口

v0.7.0 通过后才规划第二章节、第二条途径或完整收藏系统。当前优先让抽卡、升级、牌组构筑和挑战形成实际闭环。
