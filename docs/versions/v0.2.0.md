# v0.2.0 规则与接口冻结

## 1. 版本信息

- 日期：2026-11-08
- 状态：有条件关闭（规则与接口部分完成；真实运行链路转入 v0.3.0）
- 用户价值：建立一个不会因 UI、数值、存档各自实现而返工的最小可运行骨架

## 2. 版本目标

在不扩张内容量的前提下，冻结首版核心规则语义、跨模块接口、数据 schema、数值入口和存档边界。版本结束时应能可靠完成“加载内容 -> 初始化战斗 -> 执行确定性命令 -> 产生事件/快照 -> 保存并恢复进度”的最小链路。

## 3. 必须交付

### 3.1 玩法设计

- 二选一决策：首版采用“自动行动 + 玩家部署”或“玩家逐张出牌”，必须提交对比与唯一推荐。
- 战斗回合状态机：阶段、合法命令、事件顺序、胜负和异常结束。
- 领域接口职责：状态、命令、事件、只读快照、随机端口、内容端口。
- 卡牌效果的最小封闭集合，明确目标、时机、叠加和触发顺序。
- 白天身份、夜间战斗、奖励、抽卡与晋级的领域流程图。
- 可重复的规则测试列表。

### 3.2 UI 设计

- 1600×900 页面流：启动、继续/新游戏、白天、地图、战斗、奖励、抽卡、晋升、结算、错误。
- 每页低保真线框与只读视图模型字段。
- 玩家命令与界面状态的对应表。
- 资源不足、目标非法、重复点击、危险阈值等状态。
- 现有 `art/` 样例的映射和缺口清单。
- 不得实现战斗结算或读取存档。

### 3.3 数值设计

- 首局 10—20 分钟的目标节奏。
- 生命、灵性、污染、被注视度的初始范围与阈值。
- 首版伤害/护甲/治疗公式的最小版本。
- 20 张卡牌的费用分布、敌人数值区间和奖励经济。
- 抽卡概率、保底、重复卡转化和关键卡确定性获取。
- 可用固定种子运行的模拟表或公式表，不直接改玩法代码。

### 3.4 本地数据层开发

- `src/app`、`src/infrastructure`、`src/core` 的最小骨架，但只为已验证的调用方实现。
- JSON 内容加载、schema 校验和明确错误路径。
- 原子保存、读取、版本检查和最小迁移入口。
- 可注入、可复现的 RNG。
- 启动日志与错误分类。
- 基础设施测试；不实现战斗规则。

### 3.5 产品经理

- 汇总角色报告，形成唯一接口表。
- 对冲突作出 ADR。
- 检查是否存在循环依赖、重复数据和提前抽象。
- 冻结后创建 v0.3.0，不直接实现游戏功能。

## 4. 明确非目标

- 完成全部牌阵战斗内容。
- 制作正式抽卡演出和完整收藏系统。
- 多条途径、多城市、多章节。
- 完整美术替换、音频和发布导出。
- 把原型数据当作最终平衡。
- 建立插件、mod、服务器或联网框架。
- 为尚未出现的第二个调用方制作通用事件总线。

## 5. 依赖顺序

```text
玩法语义草案
  -> 数值参数映射与 UI 信息需求
  -> 产品经理接口裁决
  -> 最小领域实现
  -> UI 接线与数据层接线
  -> 确定性集成验证
```

并行安全规则：

- UI 可以先画页面与交互，但不得定义结算语义。
- 数值可以先提出目标区间和表结构，但不得把未批准参数写入玩法。
- 数据层可以先实现通用原子保存、schema 校验和 RNG，但不得替玩法生成最终状态。
- 玩法可以在自己的报告中定义接口草案，但共享 `src/core` 只有在 PM 冻结后才能创建。

## 6. 公共接口最低要求

玩法设计必须在报告中回答：

- 状态只读还是可通过组件任意修改？
- 命令是否幂等，重复点击如何处理？
- 事件按什么顺序产生，UI 动画与结算如何解耦？
- 卡牌选择、目标选择、取消和非法操作如何表达？
- 随机抽取在哪个时点结算，种子和日志在哪里记录？
- 战斗失败属于流程状态还是异常？
- 抽卡、升级、晋升分别属于哪个应用用例？
- 数据层通过哪些端口被调用？

## 7. 数据与路径要求

- 所有内容使用稳定 ID，不以中文显示名为键。
- 所有数值从 `data/balance/**` 进入，不散落在脚本。
- UI、玩法、基础设施不得各自拼资源路径；通过内容注册表/数据引用。
- 不在多个模块重复定义枚举、效果 ID 或存档字段。
- 新增 schema 必须带版本与校验器。

## 8. 验收标准

- 两名角色对同一核心词的含义无歧义。
- 战斗命令和事件能覆盖正常流程、取消、非法操作与结束。
- UI 能仅依据视图模型/事件显示状态，不读取领域内部字段。
- 数值参数有唯一来源，可被测试读取。
- 内容加载失败、存档损坏和迁移失败都有明确行为。
- RNG 使用固定种子可重复。
- 最小链路可在 Godot headless 模式验证。
- 没有出现 S0/S1 Bug、循环依赖、绝对路径或重复主数据源。

## 9. 风险与回滚点

| 风险 | 对策 |
|---|---|
| 接口过早复杂化 | 只覆盖首版真实流程，由 PM 删除无调用方抽象 |
| UI 先做后改 | 先以状态清单和低保真线框验证信息需求 |
| 数值和规则同时变更 | 规则语义先冻结，参数独立进入版本 |
| 数据层成为业务层 | 依赖检查，规则留在 gameplay |
| 多角色同时改 core | PM 指定唯一接口负责人，其他角色只提交请求 |

绿色检查点：Godot 项目无解析错误，原有美术与工程文件不被破坏。接口冻结前不建立大规模测试框架或第三方依赖。

## 10. 下一版本入口

v0.2.0 通过后创建 v0.3.0“单场牌阵战斗垂直切片”，目标是完成一场从开始到胜负、事件表现和结算可验证的战斗。v0.3.0 不加入抽卡和完整晋升系统。

## 11. 关闭结论

- 关闭日期：2026-11-08
- 关闭类型：有条件关闭，不视为完整运行链路验收通过。
- 已完成的稳定成果：
  - ADR-0002、ADR-0003、ADR-0004 已冻结文件所有权、逐张出牌、单占卜家、术语和压力时点。
  - `src/core/**` 已有命令、事件、只读快照、Playability 和三个端口。
  - `src/gameplay/**` 已实现最小逐张出牌战斗核心，报告记录 headless `52 checks passed`。
  - `src/infrastructure/**`、`src/app/**` 和 schema 已实现内容加载、端口适配、RNG、日志、原子存档和迁移入口，报告记录 headless `59 passed`。
  - `assets/ui/**` 已有 10 张页面线框和独立 Godot 静态预览。
  - `data/balance/v0.2.0/**` 已有 20 卡、6 敌人、奖励和抽卡草案，固定种子模拟与 7 项数值测试已有记录。
- 尚未通过完整验收的部分：
  - 没有正式 `data/cards/**` 和 `data/enemies/**` 数据，真实战斗只通过隔离夹具验证。
  - 新游戏启动、战斗、结算和继续游戏尚未完成跨模块接线。
  - UI 生产页面未接入 BattleSnapshot/Command；角色报告仍有 `pollution` 旧字段文字，必须在 v0.3.0 修正。
  - 当前玩法实现的压力时点仍是旧的第 7 回合规则，尚未按 ADR-0004 改为第 5/7/9 回合。
  - 数值模拟尚未在 ADR-0004 时点下重新采样，谨慎构筑 99.46% 胜率仍未解决。
  - 资源仍位于 `art/assets/**`，正式 `assets/game/**` 迁移未执行。
  - 不支持战斗中恢复是已批准限制，但继续游戏与结算检查点仍需真实集成验证。

## 12. 角色需求、困难与解决记录

| 角色 | 本版本需求 | 遇到的困难 | 最终处理 | 转入后续的事项 |
|---|---|---|---|---|
| 产品经理 | 冻结唯一玩法、术语、存档和模块接口 | 多个角色的出牌模式、节点数、失败代价、字段名和压力规则冲突 | 用 ADR-0002/0003/0004 做唯一裁决，历史报告不改写 | 关闭条件、集成验收和版本路线 |
| 玩法设计 | 给出可实现的战斗状态机并建立最小核心 | 自动战斗吸引力不足；共享契约未冻结；测试入口生命周期不稳 | 选择逐张出牌 + 三列即时目标；冻结后创建 core；改用 Godot 场景测试入口 | ADR-0004 压力时点、正式卡牌数据和真实 UI 接线 |
| UI 设计 | 页面流、线框、只读视图模型和命令边界 | 容易在按钮回调复制规则；页面状态过多 | 每流程一个页面，覆盖层处理确认；先做静态预览 | `corruption` 文档对齐、正式战斗页和路由 |
| 数值设计 | 10—20 分钟节奏、20 卡和抽卡经济 | 初期胜率过高；压力规则在聚合模拟中几乎不生效 | 先调基础参数不叠特殊规则；把无效压力作为结构问题时序上报 | 按第 5/7/9 回合重采样，真实 BattleEngine 后复核 |
| 本地数据层 | schema、加载、RNG、日志、原子存档和端口适配 | 迁移前错误执行当前校验；类缓存导致冷启动失败 | 重构为解析→迁移→当前校验；适配器实例化上移到应用入口 | 正式卡牌/enemy/encounter schema 与真实内容 |
| 主协调者 | 建立环境、派工和最终验收 | PowerShell 与 Bash 语法混用产生 `$null` 文件 | 精确删除并登记 BUG-0002；后续强制 shell 与语法一致 | 资源受控迁移和集成测试所有权 |

## 13. 移交 v0.3.0 的硬门槛

以下项目不是可选增强，必须在 v0.3.0 关闭前完成或再次明确降级：

1. 正式内容数据通过 schema 校验。
2. 新游戏可直接进入一场真实战斗，UI 只消费快照并发送命令。
3. ADR-0004 压力时点由玩法实现和测试证明。
4. 胜负结果可保存为一个明确检查点，重新启动后可读取摘要。
5. 固定种子重复执行得到相同事件顺序和快照。
6. 不存在 `pollution` 运行字段、绝对路径、循环依赖或重复主数据源。
