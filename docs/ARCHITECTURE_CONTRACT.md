# 架构契约

## 1. 目的

在编写玩法代码前固定模块边界，防止 UI、规则、数值、存档互相渗透。架构以“足够完成首版”为上限，不建立无实际调用方的空框架。

## 2. 目标目录

目录在首次实现对应模块时创建；v0.1.0 不创建空代码目录。

```text
G:\guimizhizhu\

  AGENTS.md
  art\                    # 美术源文件、生成脚本和预生产资产管理
  assets\                 # 游戏实际引用的稳定资源，按内容版本迁移
  data\
    schema\               # 数据 schema 和版本
    cards\                # 卡牌定义，按稳定 ID 建文件
    enemies\              # 敌人定义
    encounters\           # 战斗遭遇
    routes\               # 短路线节点与路线状态配置
    rituals\              # 晋升仪式步骤与选项
    challenges\           # 数据驱动挑战与修饰，不复制路线规则
    decks\                # 牌组合法性与预设内容，只保存稳定卡牌 ID
    balance\              # 数值表
```

## 3. 模块职责

### `src/core`

- 只放跨模块稳定契约：ID 类型、命令、事件、只读快照和基础枚举。
- 不包含具体战斗公式、UI 文案或文件读取。
- 修改需要产品经理确认，避免所有角色同时改公共类型。

### `src/gameplay`

- 拥有战斗、卡牌效果、敌人意图、抽卡结算、牌组合法性、成长和晋升状态机。
- 接收命令，输出事件和只读快照。
- 不创建 `Control`，不访问场景树，不弹窗，不读写文件。
- 不持有全局随机数；从注入的随机端口取数。
- 不包含展示名称和 UI 排版。
- 牌组与挑战只编排既有战斗/路线/成长用例，不派生第二套流程状态机。

### `src/ui`

- 负责页面、组件、输入、动画和可访问状态。
- 通过只读视图模型显示状态，通过命令提交操作。
- 不得直接改变领域对象、抽卡概率、伤害结果或存档字段。
- 不根据卡牌名称写特殊规则；特殊行为来自数据与玩法层。

### `src/infrastructure`

- 实现 JSON 内容加载、数据校验、存档、迁移、本地日志和可复现 RNG。
- 只实现端口，不决定游戏规则。
- 不引用 UI 场景。
- 对损坏数据给出明确错误，不能静默使用默认值覆盖用户存档。

### `src/app`

- 唯一装配具体模块的位置。
- 负责启动流程、场景路由和功能开关。
- 不在应用层复制玩法规则。
- 不允许 UI 自行访问基础设施单例；依赖由应用入口注入。

## 4. 允许的依赖方向

```text
src/ui              -> src/app, src/core
src/app             -> src/gameplay, src/core
src/gameplay        -> src/core
src/infrastructure  -> src/core
src/app/bootstrap   -> src/ui, src/gameplay, src/infrastructure
```

具体约束：

- `core` 不依赖其他项目模块。
- `gameplay` 不依赖 `ui`、`infrastructure` 或 `app`。
- `infrastructure` 可以实现 `gameplay/app` 所需的端口，但不得反向让玩法依赖实现类。
- `ui` 不得导入 `gameplay` 内部状态类；使用 `core` 中的视图模型或命令。
- 禁止通过全局 autoload 隐藏依赖；确需全局服务时在 ADR 中说明并由应用入口注册。

## 5. 状态与命令

- 领域状态只由玩法层命令改变。
- UI 只发送意图，例如“选择卡牌”“结束回合”“购买抽取”，不直接计算结算。
- 玩法层输出不可变快照和事件，例如 `CardDrawn`、`DamageApplied`、`CorruptionChanged`。
- UI 根据事件播放动画；动画不能决定结算结果。
- 同一个操作在规则上必须只产生一次结算，即使 UI 重复点击。

## 6. 卡牌数据

卡牌至少包含：

```json
{
  "schema_version": 1,
  "id": "card.identity.reporter",
  "category": "identity",
  "cost": {"spirit": 2},
  "target": "self",
  "effects": [
    {"effect_id": "reduce_attention", "amount": 1}
  ]
}
```

- 稳定 ID 一旦被存档或关卡引用，不随显示名称改变。
- 卡牌实际逻辑通过已注册的 `effect_id` 组合表达。
- 禁止内容数据直接引用任意脚本路径。
- 文本字段可以本地化，但 ID 和效果参数不本地化。
- 新效果必须同时定义合法目标、触发时机、叠加规则和日志字段。
- 卡牌自身的效果参数（例如伤害、护盾、费用和状态层数）以 `data/cards/**` 中的唯一卡牌定义为准。
- `data/balance/**` 维护全局战斗参数、经济和概率，不复制卡牌定义；数值设计审核卡牌金额，但不得创建同 ID 的第二份定义。

## 7. 随机数

- 战斗、掉落和抽卡使用同一个可注入 RNG 端口。
- 每个独立流程可派生子种子，并在调试日志中记录根种子。
- 抽卡结果由数据规则和当前卡池状态决定，不由 UI 计算。
- 自动测试必须能用固定种子复现。

## 8. 存档

存档最低结构：

```json
{
  "save_version": 3,
  "content_version": "v0.5.0",
  "created_at": "ISO-8601",
  "rng_seed": 0,
  "profile": {},
  "run": {},
  "collection": {}
}
```

- 保存采用临时文件 + 校验 + 原子替换，避免中途失败破坏旧档。
- 读取顺序：解析 -> schema 校验 -> 迁移 -> 不变量检查 -> 进入游戏。
- 迁移失败时保留原文件，显示错误，不自动覆盖。
- 当前版本目标使用 `save_version: 3`；历史 v1/v2 必须通过显式迁移读取。
- 路线只在节点边界建立检查点，不保存战斗中间状态。
- UI 和玩法层不能直接写文件。

## 9. 资源与路径

- Godot 运行时路径使用 `res://`。
- 不得使用操作系统绝对路径。
- 文件名小写 `snake_case`；内容 ID 点分。
- 资源实际引用路径由集中资源注册表或数据文件保存，不允许 UI 用字符串随意拼接。
- `art/` 是美术源与预生产区；正式资产由主协调者一次性迁移到 `assets/game/<version>/**`，禁止长期维护同名双份。
- 第三方资源必须记录来源、授权和用途到 `art/ASSET_MANIFEST.md` 或后续统一资产清单。

## 10. 测试与质量门

### 领域

- 抽牌、费用、目标合法、伤害顺序、污染阈值、晋升条件。
- 相同种子和命令序列必须得到相同状态。

### 数据

- 所有 ID 唯一。
- 所有效果 ID 已注册。
- 所有资源路径存在。
- 数据 schema 版本可识别。

### 基础设施

- 存档往返、损坏存档、迁移失败、原子写入。
- 内容加载失败可诊断。

### 集成

- 从新游戏进入第一场战斗。
- 战斗结束到奖励和存档。
- 抽卡到收藏与下次战斗。
- 晋升仪式到序列变化。

## 11. 依赖升级与新依赖

新增库或插件必须记录：

- 名称、来源、版本和许可证
- 解决的问题
- 为何 Godot 内置能力不足
- 对导出、存档和升级的影响
- 移除方案

未经过产品经理与本地数据层评审，不得加入项目。
