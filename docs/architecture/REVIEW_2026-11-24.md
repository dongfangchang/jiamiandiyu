## 0. 结论摘要

项目的**分层骨架是对的**：
- `gameplay` / `core` 里没有 `Node`、`Control`、`FileAccess`、真随机。
- 没有 autoload 隐藏依赖。
- UI 没有 preload 玩法或基础设施类。
- 存档有版本链、原子写入和备份恢复。

这些是 v0.1–v0.7 打下的好地基。

问题在于 **v0.8 之后近 80 个版本都在做表现层迭代，只叠加、不回收**。由此形成四类债：

1. **规则与内容泄漏到错误的层**：
   - UI 复刻战斗公式。
   - 玩法层硬编码中文旁白和平衡数值。
   - UI 自己读 JSON。
2. **事实源分裂**：
   - 卡图路径有 4 个定义源。
   - 日记文案有 2 个定义源。
   - 内容数据散落在 v0.3/v0.4/v0.5/v0.7 四代目录，叠加加载。
3. **死代码与"为探针保留"的隐藏节点**：
   - 估计全项目可删 **3,000–3,500 行**，约占 src 的 10%。
   - 另有约 19 MB 无引用资源目录。
4. **工程地基缺失**：
   - 没有统一测试入口，也没有 CI。98 个独立 runner 中 59 个不在任何汇总脚本里。
   - 至少 3 个测试已确定会失败：它们硬编码了旧版本号。
   - 存档版本自 v0.7 冻结至今。

代码总量约 31k 行 GDScript，其中测试约 24k 行，`src/ui` 约 17k 行。在大量删除死代码并合并重复之后，src 可以从约 31k 行降到 **约 22–24k 行**，且不损失任何玩家可见功能。

**建议**：后续 4–6 个版本以"整治"为主，暂停表现层新特性，具体见 ROADMAP。先装好安全网（统一测试 + 黄金回放），再删除死代码，然后把规则收回玩法层、合并事实源，最后才拆分大文件。

## 2. 流程层面的观察

1. **版本粒度过细**：16 天发了 85 个版本，v0.57–v0.71 这 15 个版本在同一天。版本号已经不再对应"可验收的玩家价值"，而是"一次会话"。后果是文档仪式（版本文档、角色报告、索引）的成本远超产出，且每版都留下一层"为探针保留"的兼容代码。
2. **表现层反复推翻**：日记载体先后经历 2D → 伪 3D → 真 3D flip → 全屏书图 → 桌面 3D 书，旧载体没有一次被删掉。这正是 AR-42 的成因。**建议**：新载体验收通过的同一版本，必须删除旧载体及其探针。
3. **测试是"版本验收脚本"而不是"行为回归"**：测试按版本号命名，断言版本号和源码文本。版本一过，测试要么失效，要么变成重构阻力。
4. **"冻结"只冻了玩法，没冻结构**：玩法冻结期间 UI 持续膨胀，UI 为了不碰玩法层就在本地复刻规则（AR-02/03/15）。冻结不应禁止玩法层**新增只读快照字段**，否则冻结本身就在诱导越层。

## 4. 做得好的地方（保留，不要在重构中破坏）

- 依赖方向基本守住：`gameplay`/`core` 纯净，UI 不 import 玩法和基础设施，没有 autoload。
- 随机数可注入且有种子，具备做确定性回放测试的前提。
- 存档原子写入、`.bak` 备份、损坏检测和恢复流程完整，迁移链线性且单调。
- 内容 JSON 普遍带 `schema_version`，且有自研 schema 校验器。
- 稳定点分 ID 的纪律执行得好。
- `docs/bugs` 根因记录习惯好。
