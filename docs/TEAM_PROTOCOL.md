# 多智能体协作协议

## 1. 目标

让多个角色并行工作时保持同一个产品方向，减少文件冲突、重复实现、跨层耦合和无法追踪的 Bug。

## 2. 信息流

```text
用户
  -> 产品经理：需求、范围、验收和裁决
  -> 当前版本文档：唯一执行基线
  -> 角色报告：事实、依赖、困难、方案和请求
  -> 产品经理汇总：版本状态、风险、下一入口
```

聊天中的临时结论只有在产品经理写入版本文档或 ADR 后才成为项目要求。

## 3. 文档所有权

- 产品经理独占编辑：`docs/PROJECT_CHARTER.md`、`docs/TEAM_PROTOCOL.md`、`docs/ARCHITECTURE_CONTRACT.md`、`docs/CURRENT_VERSION.md`、`docs/versions/**`、`docs/decisions/**`。
- 角色独占编辑：`docs/reports/<version>/<role>.md`。
- 角色之间需要改动对方文件时，先在本角色报告写下请求，不直接编辑。
- 共享契约文件由产品经理指定一个临时负责人；同一时间只允许一个角色修改。

### 3.1 UI 与美术的审稿边界

- 美术与 UI 必须是不同角色，不能由同一角色制作并验收同一批图。
- 美术负责 `art/**` 的源文件、生成脚本、资产候选和美术制作报告。
- 正式 `assets/game/**` 由主协调者从美术候选一次性迁移；迁移后其他角色只读。
- UI 负责把正式资源接入 `src/ui/**`、`scenes/ui/**` 和 `assets/ui/**`。
- UI 必须在实际 1600×900 页面中审稿：裁切、对比度、缩小可读性、状态辨识、遮挡和安全区。
- UI 审稿结论必须写入当版本 UI 报告，分为“通过”“需要美术返工”“仅需 UI 适配”。美术不得自行标记验收通过。

## 4. 版本流程

### 4.1 开启

产品经理创建新的 `docs/versions/vX.Y.Z.md`，说明：

- 版本目标与用户价值
- 必须交付和明确非目标
- 角色任务与依赖顺序
- 公共接口和数据变更
- 验收标准
- 风险与回滚点

随后更新 `docs/VERSION_INDEX.md` 和 `docs/CURRENT_VERSION.md`。

### 4.2 执行

- 角色先写报告中的任务计划和依赖。
- 完成一个独立子任务后立即更新报告，不等到整个版本结束。
- 满足同步触发条件时重新读取版本文档，检查是否仍然在范围内。
- 发现接口不成立或范围冲突时暂停相关改动，提交决策请求。

### 4.3 关闭

产品经理逐项检查：

- 验收条件是否真的通过
- 是否有未记录的跨层修改
- 是否有临时兼容分支和未解释的补丁
- 数据、存档和公共路径是否只有一份定义
- 角色报告是否包含困难、解决方案和下一入口
- 是否存在没有版本归属的待办

通过后历史版本文档冻结；失败则记录阻塞并创建修复版本，不回写旧版本。

## 5. 同步节奏

满足任意一项时执行同步：

- 任务开始和结束
- 连续工作 30 分钟
- 累计修改 10 个项目文件
- 修改一份共享契约
- 修改数据 schema、存档格式、资源稳定 ID 或公共路径
- 发现 S1/S2 Bug
- 准备把任务交给另一个角色

同步动作：

1. 读取 `docs/CURRENT_VERSION.md` 和当前版本文档。
2. 更新自己的角色报告。
3. 核对文件所有权和依赖方向。
4. 运行当前最低质量门。
5. 有跨角色请求时等待产品经理裁决。

## 6. 角色报告

路径：`docs/reports/<version>/<role>.md`

每个版本首次出现时复制 `docs/templates/agent-report.md`。报告只由对应角色维护，产品经理读取但不代写事实部分。

必需的跨角色请求格式：

```text
[REQUEST]
从：玩法设计
给：UI 设计
版本：v0.2.0
内容：战斗命令需要显示“可打出/资源不足/目标非法”三种状态
原因：界面需要提前呈现失败原因
期望接口：BattleCardViewState.playability
截止检查点：战斗状态机草案完成时
[END REQUEST]
```

## 7. 冲突处理

- 两人需要编辑同一文件：产品经理指定唯一负责人，另一方提供补丁建议。
- UI 与规则冲突：玩法设计定义语义，UI 只呈现并发送命令。
- 数值与规则冲突：规则决定可表达的状态，数值决定参数；不得用数值掩盖状态机缺失。
- 数据层与玩法冲突：玩法定义端口需求，数据层实现；公共端口由产品经理冻结。
- 产品方向冲突：产品经理写 ADR，记录替代方案和后果。

## 8. 检查点与故障修复

- 每个可运行阶段建立 Git 检查点；提交信息包含版本和模块。
- 不提交半可运行状态作为“绿色检查点”。
- S0/S1 Bug 时停止扩展功能，先隔离故障并确认是否仍可安全运行。
- 默认采用前向根因修复：保留已验证工作，只替换或重构故障模块。
- 只有游戏无法运行、数据可能损坏、结构性问题无法安全前进或用户明确要求时，才进入回滚评估。
- 回滚前必须由产品经理记录原因、目标检查点、影响文件、恢复范围和用户影响，并明确告知是否保留无关修改。
- 禁止用回滚代替根因分析，也禁止静默丢弃其他角色的工作。
- 修复必须新增或更新对应回归验证。

## 9. 产品经理监督清单

每次监督必须回答：

- 当前工作是否属于本版本？
- 是否修改了不属于自己的文件？
- 是否引入了新的公共数据源或绝对路径？
- 是否有绕过接口直接访问 UI、文件或随机数？
- 是否用增量条件修补了结构性错误？
- 当前实现是否会让下一版本重复返工？
- 角色困难是否有记录、方案和决定？
- 文档是否能从新会话恢复全部关键上下文？

## 10. 破坏性 QA 与 Token 预算

### 10.1 破坏性测试职责

QA 的任务是让系统在错误状态下暴露问题，不允许只沿着开发的正常路径逐项点击：

- 重复与连点：抽卡、出牌、结束回合、确认退出、领取奖励、开始挑战。
- 非法阶段：战斗结束后继续操作、缺牌确认牌组、锁定挑战开始、错误页面发送命令。
- 资源边界：零券、零费用、费用不足、满生命、满护盾、污染和注视达到上限。
- 中断与乱序：pending 返回、取消确认、切页、迟到结果、超时回调晚于结果、重复快照。
- 存档破坏：截断主档、损坏备份、缺失槽位、版本过高、恢复后重启。
- 隔离：测试档案与普通档案互不污染；失败重试不复制收藏或奖励。
- 显示：全部内容中文名、图像、未知原因码、未知状态 ID 和空数据回退。

测试先从根因可能影响的状态机、存档事务、异步回调、路由和 UI 锁定入手，不以“按钮存在”作为通过证据。

### 10.2 最小测试集

- 单模块逻辑修改：跑对应领域/UI 测试和最近版本的破坏性专项。
- 跨 UI 与应用路由修改：增加真实按钮流和应用集成。
- 存档、schema、迁移或恢复修改：必须增加损坏、恢复、重启和隔离测试。
- 发布候选：运行 `tools/run_v091_qa.ps1 -Full`，全部 28 组通过后才允许构建。
- 如果无法判断影响面，扩大测试集；不得因 Token 预算跳过存档或运行阻断回归。

### 10.3 Token 预算责任

产品经理直接负责每阶段 Token 预算，所有角色共同执行：

- 同一任务中已读取且未变化的长文档不重复读取。
- 优先用 `rg` 和目录清单定位文件，只读取相关段落。
- 验证输出只保留最终 PASS/FAIL 标记和失败上下文，不反复粘贴完整构建日志。
- 角色报告记录事实、证据、风险和下一入口，不复制聊天全文。
- 最小测试集用于日常迭代，版本门才执行全量；不得用“全量重跑”代替根因分析。
- 预算冲突时，优先保留破坏性回归、存档安全和可运行构建。

### 10.4 版本门

任何版本发布前必须同时具备：

- 统一全量 QA PASS。
- 当前版本破坏性专项 PASS。
- 实际截图或等效窗口验收。
- 独立构建在项目目录外启动成功。
- QA 与产品经理证据一致，构建哈希写入版本报告。

### 10.5 缺陷分流与非阻断并行

- “按钮不可用”本身不自动等于阻断。若当前没有合法下一步、无法返回/取消且只能强制关机，按 S1 处理。
- 如果按钮按业务规则暂时不可用，但页面仍有合法继续动作，按 S2/S3 处理；文案必须说明真实可执行动作。
- S3 视觉、文案和低频布局问题进入当前小型补丁或候选池，不得冻结无关功能版本。
- S1、数据破坏或持续崩溃必须立即停止相关扩展；测试可继续验证上一个稳定构建并守卫回归。
- 非阻断测试问题可按模块分派给独立智能体处理，但同一文件只能有一个写入负责人。
- QA 提出缺陷后，产品经理按 S0/S1/S2/S3 分流；开发、UI、玩法可继续处理互不冲突的任务。
- 低版本验证用于证明新问题不是既有回归，不替代当前版本发布门。
