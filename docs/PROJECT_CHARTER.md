# 项目章程：假面低语

## 1. 文档信息

- 产品暂定名：《假面低语》
- 工作路径：`G:\guimizhizhu`
- 产品类型：单人、离线、Godot 桌面卡牌游戏
- 背景：原创的《诡秘之主》同人支线
- 使用范围：仅本人本地游玩
- 基线版本：`v0.1.0`
- 文档负责人：产品经理

## 2. 用户需求复述

用户希望在当前文件夹制作一个能够自己游玩的离线游戏，使用《诡秘之主》背景，不包含多人功能。项目需要低成本、由个人或少量智能体协作完成，并尽快形成可玩的大致版本。

玩法需要包含升级和抽卡，不采用以解谜为主的结构。途径和序列晋升可以加入少量、短时、不会长期卡人的解谜或仪式选择。

项目由多个智能体分工推进：

- UI 设计负责界面、交互和信息呈现。
- 玩法设计负责核心循环、规则与状态转换。
- 数值设计负责成长曲线、战斗公式、经济与抽卡概率。
- 本地数据层开发承担用户所说的“后端”，包括离线存档、内容加载、随机数与基础服务。
- 产品经理负责需求、版本文档、开发路线、验收和跨角色监督。

用户特别强调：

- 出现 Bug 时先找根因，避免在错误结构上不断做增量补丁。
- 路径、依赖和级联修改必须规范。
- 每个版本使用一个新文档，保留历史记录。
- 每个角色在不同版本中的需求、困难、解决方案和风险都要有记录。
- 可以定时或按修改量读取和同步文档。
- 产品经理必须防止其他角色偏离范围、提前承诺或为后续开发埋坑。

## 3. 产品目标

### 3.1 核心承诺

玩家是一名在普通人身份与非凡力量之间维持平衡的非凡者。白天依靠身份牌获取资源和维持伪装，夜晚以牌阵对抗异常并收集成长资源。力量、污染和被注视度同时上升，序列晋升必须承担代价。

### 3.2 核心体验支柱

1. **扮演与失控的拉扯**：使用力量能解决眼前问题，也会改变身份状态和后续风险。
2. **可理解的牌阵决策**：玩家通过部署卡牌、消耗灵性和选择时机形成组合，不依赖手速。
3. **有目标的收集**：抽卡提供构筑变化和惊喜，主线晋升由确定性的游戏进度保障。
4. **短局与持续成长**：单局目标为 10—20 分钟，局外升级推动下一次尝试。
5. **微量仪式解谜**：晋升试炼控制在 30—90 秒，失败增加代价或降低奖励，不形成硬卡关。

## 4. 当前产品假设

以下内容可在编号版本中修改，但不得由单个开发角色静默改变：

- 基准窗口为 `1600 x 900`，使用 Godot 4.7.2 标准版和 GDScript。
- 首版只实现一条可玩路线，后续再评估第二条途径。
- 抽卡只消耗游戏内资源，不包含真实货币。
- 一局由若干战斗、一次短仪式或事件、一次局外成长组成。
- 存档为本地文件，可离线完成全部玩法。
- 美术使用现有 `art/` 资产作为原型基线，正式补充遵循 `art/ART_DIRECTION.md`。

## 5. MVP 范围

### 5.1 必须实现

- 新游戏、继续游戏和退出。
- 一张短地图或连续遭遇流程。
- 可操作的回合制牌阵战斗。
- 至少 20 张可用卡牌和 6 种敌人。
- 生命/灵性/污染等最少必要状态。
- 局内奖励与局外升级。
- 一次可验证的抽卡流程，包含保底或确定性获取机制。
- 至少一次序列晋升，包含短仪式选择。
- 自动保存、手动继续和基础错误提示。
- 至少一个完整胜利结局和一个失败结局。

### 5.2 明确不做

- 多人、联网、账号、云存档或服务器。
- 开放世界、自由行走、多城市主线。
- 完整二十二条途径。
- 实时战斗、逐帧人物动画、3D 场景。
- 真实货币、广告、运营活动或社交系统。
- 依赖高难度解谜推进主线。
- 插件市场、通用 mod 系统或提前为未知需求设计复杂框架。

## 6. 角色职责

### 产品经理

- 维护章程、当前版本、历史版本、ADR 和路线。
- 把用户需求转成可验收范围。
- 审核跨模块接口、共享数据和版本关闭条件。
- 读取各角色报告，阻止范围漂移和技术债积累。
- 决定何时升级版本，不因单个功能完成而自动升版。

### UI 设计

- 设计信息架构、页面流、线框、交互状态与视觉层级。
- 将领域状态映射为只读视图模型，向玩法层发送明确命令。
- 负责 UI 场景与组件，不制定战斗胜负、抽卡概率或伤害规则。

### 玩法设计

- 定义核心循环、状态机、卡牌语义、触发顺序和边界条件。
- 提供稳定领域接口与可测试规则。
- 不依赖具体 UI、文件保存或平衡数值。

### 数值设计

- 定义战斗公式、经济产出、升级成本、抽卡概率与保底。
- 建立可重复的模拟与调参记录。
- 不直接修改流程规则或把数值硬编码进生产代码。

### 本地数据层开发

- 实现离线内容加载、存档迁移、随机数、日志和应用装配。
- 为玩法层提供接口，不让基础设施逻辑渗入业务或 UI。
- 保证数据校验、可复现测试和失败恢复。

## 7. 成功标准

首版试玩必须满足：

- 新玩家在无口头说明的情况下 5 分钟内理解白天选择、夜间战斗和成长的关系。
- 单次游玩可在 20—30 分钟内形成一次明显升级或序列变化。
- 卡牌选择存在至少两个可理解的方向，不依赖唯一最优解。
- 抽卡提供构筑变化，但不会因运气导致无法继续。
- 晋升仪式不要求外部资料，不因一次错误永久卡死。
- 连续三次启动、存档、读取不丢失关键进度。
- 关键规则有可重复验证，重大 Bug 有根因与回归记录。

## 8. 约束与风险

| 风险 | 影响 | 应对 |
|---|---|---|
| 角色并行造成接口冲突 | 返工、循环依赖、互相覆盖 | 分阶段交付，PM 仲裁，共享契约单一负责人 |
| 卡牌系统范围膨胀 | 无法短期可玩 | 首版单路线、少量卡牌、效果字典有上限 |
| 抽卡随机破坏体验 | 卡关或反复刷取 | 主线关键卡确定性获取，保底、重复卡转化 |
| UI 与技术实现互相渗透 | Bug 难定位、后续扩展困难 | 视图模型与命令接口，依赖方向强制单向 |
| Bug 修补累积 | 状态不可预测、路径级联 | 根因修复、回滚绿色检查点、替换故障模块 |
| 文档与实现不一致 | 智能体跑偏 | 每任务与每版本读取文档，PM 关闭版本前核对 |

## 9. 决策与变更

- 任何改变 MVP、分层方向、数据主键或存档结构的请求都必须形成 ADR。
- 角色不得在报告中把“建议”当成“已批准”。
- 产品经理批准后，由当前版本负责人更新版本文档，再通知相关角色。
- 历史版本不可重写；需要修正时创建新版本，并在新文档中引用被替代的版本。
