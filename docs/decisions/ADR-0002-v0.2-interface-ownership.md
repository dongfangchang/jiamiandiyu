# ADR-0002：v0.2.0 接口与文件所有权

## 状态

已接受。

## 背景

玩法、UI、数值和本地数据层会同时需要共享类型、数据 schema 和测试目录。若不先指定唯一负责人，容易产生重复定义、循环依赖和多人覆盖。

## 决策

### 共享契约

`src/core/**` 在 v0.2.0 期间由玩法设计担任唯一修改负责人。

- 玩法设计负责稳定 ID、命令、事件、只读快照和基础枚举。
- UI、数值和本地数据层只能读取并在各自报告中提出接口请求。
- 如果接口变更影响存档或 UI，产品经理必须先确认并形成 ADR 或版本文档更新。

### 数据 schema

`data/schema/**` 由本地数据层担任唯一修改负责人。

- 本地数据层负责 schema 版本、校验入口和错误结构。
- 玩法设计拥有数据语义，数值设计拥有参数内容，二者不得自行建立第二套 schema。
- schema 变化必须通知产品经理、玩法设计和数值设计，并附迁移与验证说明。

### 测试目录

- 玩法设计：`tests/gameplay/**`
- UI 设计：`tests/ui/**`
- 数值设计：`tests/simulation/**`，无 UI 测试时可直接使用模拟脚本
- 本地数据层：`tests/infrastructure/**`
- 跨模块集成测试由产品经理指定唯一负责人，不默认由任何角色并行编辑。

### 资源

- UI 拥有 `assets/ui/**`。
- 游戏通用美术资源的唯一迁移和注册表负责人由产品经理在 v0.3.0 前指定。
- 在正式迁移前，已有 `art/assets/**` 可作为只读预览来源；不得另建同名副本长期并行维护。

## 并行边界

- 玩法先冻结接口语义，其他角色可做不依赖实现细节的草案。
- UI 不得导入玩法内部状态，只使用冻结后的视图模型和命令。
- 数值只通过参数 ID 读写 `data/balance/**`。
- 本地数据层不得替玩法生成战斗状态或抽卡结果。
- 任何角色修改 `src/core/**`、`data/schema/**` 或 `project.godot` 前必须停止并请求负责人。

## 后果

- 共享契约只有一条写入路径，降低冲突。
- 关键路径先经过玩法接口评审。
- 产品经理需要及时裁决跨角色请求，避免唯一负责人成为长期瓶颈。

## 检查点

v0.2.0 关闭前检查：

- 是否存在第二套共享类型。
- 是否有 UI 读取玩法内部状态。
- 是否有数值硬编码绕过 balance。
- 是否有 schema 被玩法或数值角色私自修改。
- 是否有测试目录跨角色覆盖。
