# ADR-0037：画面"目标帧先行"——先定稿图，再写代码

状态：已采纳（用户 2026-11-25："初始界面和日记界面太简陋，改了几版都不满意"）
日期：2026-11-25
关联：ADR-0032（书桌世界）、ADR-0034（文字控件与可读性）、ADR-0036（渲染器：Mobile）

## 背景

v0.84 到 v0.89，标题页和日记页的画面改了 5 版以上，用户每次都不满意。复盘发现，问题不在执行，而在**没有目标**：

1. **没有一张"用户认可的目标画面"。** 每一版都由智能体自行理解"不要简陋"，然后用户看实机截图否决。验收标准是一句形容词，无法收敛。
2. **画面是"拼"出来的。** 程序生成的方块桌和墙、逐个物件单独生成的 AI 贴图（光向、透视、色温各不相同），再加上程序光照。没有统一的光和构图，就算单件素材很精致，整体也显得廉价和平。
3. **评估顺序反了。** 先实现、后看效果，每一轮都要花几小时开发，用户才第一次看到结果。

## 决策

### D1 每个站位先有一张"目标帧"

- **目标帧** = 一张 1600×900 的完整画面定稿图（绘制或合成都可以），包含最终的构图、光照、色调、物件、文字位置和氛围。它就是"做出来应该长这样"。
- 流程：
  1. 美术出 **3 个风格方向**的概念图（每个方向对标题页和日记页各出一张）。
  2. **用户挑一个方向**，并在图上指出要改的地方。
  3. 美术按批注修改，直到**用户签字**定稿。
- **在目标帧被用户签字之前，任何人不得为该站位做画面相关的代码实现。** 功能性改动（可读性、文字控件、逻辑）不受此限。

### D2 实现以"对着目标帧"验收

- UI 实现完成后，在同一分辨率下截图，与目标帧并排放进报告（`docs/reports/<ver>/target_frame_<station>.png`）。
- 验收问题只有一个："实机截图和目标帧是否看起来是同一张画？" 由用户判断。
- 允许为了实现做的取舍（例如动态光影替代手绘高光），但必须在报告里逐条列出。

### D3 实现方式服从目标帧

- 如果目标帧用"3D 程序场景 + 贴图"做不到，允许改用**整幅绘制的场景底图（按站位分层：远景 / 桌面 / 前景）**，再叠加可交互的书页和文字。这不违反 ADR-0032：书桌仍然是同一张，只是表现手段从程序几何换成分层绘制。
- 是否采用分层绘制，由架构师在目标帧签字后评估，写进该站位的实现说明。

### D4 用户需要提供的东西（最少）

1. **参考图 3–5 张**（游戏截图、插画、电影画面都可以），每张一句话说明喜欢它的什么（光？色调？物件密度？质感？）。
2. 在 3 个方向里**挑一个**，并在图上**圈出不满意的地方**。
3. 对定稿帧**签字一次**。

## 后果

- UI-P0-3（日记画面升级）和标题页的画面类工作**暂停**，等目标帧定稿。已合入的功能（文字菜单、可读性底线、遮挡修复）保留。
- 美术新增任务 ART-KEY（三方向概念图）。
- 用户对画面的反馈从"太简陋"变成"在这张图上改这里"，迭代可以收敛。
